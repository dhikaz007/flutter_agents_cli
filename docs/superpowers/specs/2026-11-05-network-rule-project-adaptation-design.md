# Network rule project adaptation — design

Date: 2026-11-05
Status: approved
Scope: profile `vibe-coding-rules`, concern `network`

## Problem

`templates/rulesets/vibe-coding-rules/rules/NETWORK.md` installs the same text
for every project: it names the source project's `ApiClient`,
`AuthInterceptor`, `IdempotencyInterceptor`, and `ConnectivityService` whether
or not the target project has them, and its two `TEMPLATE-PROJECT:` markers
(idempotency mechanism, offline mutation policy) are never filled by any code.
A project such as LMS-ECampus gets a network rule that does not describe its
code.

## Decision

Approach 1: probe inside the generator. One new module detects network facts
from the project, adapts the rule text at install time, and feeds the result
through the existing desired-file map so the plain and merged branches both
receive the adapted text. No new command, no new installed file.

## Design

### 1. Probe — `lib/src/network_probe.dart`

`NetworkProbe.detect(Directory project)` returns `NetworkFacts`:

- `packages`: dependency names from `pubspec.yaml` matching
  `dio`, `chopper`, `retrofit`, `connectivity_plus`, `http`.
- `classes`: entries of `(name, relativePath)` matched by
  `class <Name>` where `Name` ends with `Interceptor`, `ApiClient`,
  `ApiService`, or `ConnectivityService`, scanned from `lib/**/*.dart`
  excluding `*.g.dart` and `*.freezed.dart`.
- `idempotencyPaths`: files under `lib/` whose source contains the literal
  `idempotency` (case-insensitive).

Empty lists are valid results. The probe never guesses; it reports only what
it reads.

### 2. Transform — `NetworkAdaptation.apply(String ruleText, NetworkFacts facts)`

Two steps, both deterministic:

1. **Inline markers.** Every line in the rule that starts with
   `TEMPLATE-PROJECT:` is replaced, matched by keyword: a marker containing
   `Idempotency` is the idempotency slot, a marker containing `offline` is
   the offline slot, any other marker falls to the generic case:
   - idempotency slot: detected evidence →
     ``Detected `Idempotency-Key` usage at `path`.``; otherwise
     `Not detected in this project — decide the idempotency mechanism manually.`
   - offline slot: connectivity-related classes found → listed with paths;
     otherwise `Not detected — decide the offline mutation policy manually.`
   - any other `TEMPLATE-PROJECT:` line →
     `Not auto-detected — decide manually.`

   When `facts.isEmpty`, `apply` returns the input unchanged — no marker is
   filled and no section is appended.
2. **Reality section.** When any fact group is non-empty, append:

   ```markdown
   ## Project reality (generated by flutter-agents)

   - HTTP packages: dio, connectivity_plus (pubspec.yaml)
   - ApiClient: `ApiClient` — lib/core/network/api_client.dart
   - Interceptors: `AuthInterceptor` (lib/...)
   - ApiService: ...
   - Connectivity: `ConnectivityService` (lib/...)
   - Idempotency evidence: `lib/...`
   - Regenerated on sync. To customize, add a project rule for this concern
     instead of editing this file.
   ```

   Only non-empty groups appear. With no facts at all the rule text is
   returned unchanged (byte-identical), so behavior without network code
   stays exactly as today.

### 3. Integration — `lib/src/generator.dart`

In the ruleset concern loop (where `dynamicBytes` is read), when
`concern == 'network'`:

```dart
dynamicBytes = utf8.encode(
  NetworkAdaptation.apply(String.fromCharCodes(dynamicBytes),
      NetworkProbe.detect(project)),
);
```

placed before the merged/plain branch, so both `docs/dynamic-rules/rules/NETWORK.md`
and `docs/dynamic-rules/merged/network.md` carry the adapted text. No other
concern is touched.

### 4. Tests — `test/network_probe_test.dart`

- Fixture project: pubspec with `dio` + `connectivity_plus`,
  `lib/core/network/api_client.dart` (`class ApiClient`),
  an `AuthInterceptor` class, a file containing `Idempotency-Key` →
  `NetworkFacts` correct.
- `NetworkAdaptation.apply`: both markers replaced; reality section appended;
  empty facts → output byte-identical to input.
- Integration: `RuleGenerator().apply` with a ruleset that ships a
  `network` concern on the fixture → installed
  `docs/dynamic-rules/rules/NETWORK.md` and the merged view contain the
  section; marker lines are gone.
- Existing suite stays green (91 tests).

### 5. Acceptance

Copy LMS-ECampus to a temp directory, run the generator against the copy with
its own configuration, and show the produced `NETWORK.md`. The real project is
never written to.

### 6. Documentation (at commit time)

- README: note under the network/rules section that installed network rules
  adapt to detected project code.
- CHANGELOG: `## Unreleased` entry.

## Non-goals

- Other concerns' `TEMPLATE-PROJECT:` markers (UI, SECURITY, CODEGEN,
  ENVIRONMENT) stay manual.
- No heuristic filling of policy decisions the code cannot prove.
- No new CLI command, no new installed document, no router changes.
